# RECORD · 개인용 운동 트래커

완전히 새 코드베이스로 만든 Android용 운동 기록 PWA입니다. 초기 실제 1RM은 스쿼트 100kg, 벤치프레스 80kg, 데드리프트 120kg입니다. 별도 로그인·서버·외부 라이브러리 없이 GitHub Pages에서 실행합니다.

**전달 상태 (v1.0.1):** Node 자동 테스트 **38개**, 실제 Chrome IndexedDB 통합 테스트 **20개** 통과. 자유운동·척도 기록 저장, 페이지 재실행, 임시 입력 복원, 캘린더 조회·수정, 320–430px 메인 화면 가로 넘침 검사를 수행했습니다. 상세 범위는 `TEST_REPORT.md`에 있습니다. **Android 실기기 설치·프로세스 강제 종료·HTTPS 서비스워커의 실제 오프라인/업데이트 동작은 아직 미검증**입니다.

v1.0.1에서는 첫 실행의 UUID 지원 차이를 보완하고, 저장 직전 원본 손상 감지와 복구 확인 중 다른 탭 변경 감지를 추가했습니다. schema 1과 DB 이름은 그대로이므로 v1.0.0 기록을 유지합니다.

## 1. GitHub Pages 업로드

1. ZIP 압축을 해제합니다.
2. GitHub에 새 저장소를 만듭니다. 기존 운동 앱 저장소·주소는 그대로 두고 새 저장소를 사용하세요.
3. `workout-tracker` 폴더 **안의 파일과 tests 폴더**를 저장소 최상위에 업로드합니다. `index.html`이 저장소 최상위에 있어야 합니다. ZIP 자체를 업로드하는 방식이 아닙니다.
4. 저장소 **Settings → Pages → Build and deployment → Source: Deploy from a branch**를 선택합니다.
5. **main / (root)**를 선택하고 Save 합니다. 배포가 완료되면 Pages에 표시되는 HTTPS 주소를 엽니다.
6. 처음에는 **새 기록 시작**, 기존 백업이 있다면 **백업 불러오기**를 선택합니다.

파일을 더블클릭해 `file://`로 열면 모듈·서비스워커가 제대로 동작하지 않습니다. 반드시 HTTPS 웹 주소에서 사용하세요. 정적 파일이므로 별도 npm 설치나 빌드가 필요 없습니다.

공식 안내: [GitHub Pages 게시 소스 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

## 2. Android PWA 설치 및 최초 확인

1. Android Chrome에서 배포 주소를 엽니다. 시크릿 모드는 사용하지 마세요.
2. Chrome 메뉴에서 **홈 화면에 추가 / 앱 설치**를 선택합니다. 기기와 Chrome 버전에 따라 표시가 다릅니다.
3. 홈 화면 아이콘으로 앱을 열고 **데이터**에서 영구 저장 상태를 확인합니다. 미승인이면 **영구 저장 요청**을 누릅니다. 승인 여부는 Chrome이 결정합니다.
4. 먼저 테스트용 **3대운동 X → 가슴·팔 → 운동 추가 → 실제 중량·반복·RIR 입력 → 완료 체크 → 오늘 운동 완료 및 기록하기**를 수행합니다.
5. 앱을 닫았다 다시 열어 기록 1회 및 선택부위가 캘린더에 남는지 확인합니다.
6. JSON 백업을 다운로드하고 파일이 실제로 다운로드 폴더에 있는지 확인합니다.
7. 온라인 상태로 다시 열어 오프라인 파일 준비를 마친 다음, 비행기 모드에서 앱을 열어 화면과 기록이 유지되는지 확인합니다.
8. 위 확인이 끝난 뒤 실사용하세요. 테스트 운동은 캘린더에서 삭제할 수 있고 삭제 전 snapshot이 남습니다.

**앱 설치는 클라우드 백업이 아닙니다.** 브라우저 사이트 데이터 삭제, 기기 초기화, 분실, 다른 Chrome 프로필로 전환하면 접근 가능한 데이터가 달라지거나 없어질 수 있습니다. 영구 저장 승인은 저장공간 부족에 따른 자동 삭제 위험을 낮추는 기능이며 사용자의 직접 삭제까지 막지는 못합니다. [Persistent storage 설명](https://web.dev/articles/persistent-storage)

## 3. 평소 운동 기록

- 메인에서 6개 세션 또는 3대운동 X를 직접 선택합니다. 6개 순서는 강제가 아닙니다.
- 6사이클 완료 후 다음 추천은 방금 완료한 데이의 다음 순번입니다.
- 3대운동 X는 가슴·등·어깨·하체·팔 중 1개 이상을 복수 선택합니다. 운동 횟수·히스토리에만 반영하며 3대 상태와 순서는 그대로 유지합니다.
- 모든 세션에서 컨디션·피로·수면·불편감 1–5와 전후 메모를 기록합니다. 컨디션 입력이 자동 감량을 유발하지는 않습니다.
- 추천과 실제 값은 분리됩니다. **실제 kg·반복·RIR을 직접 입력하고 완료를 체크**합니다. 완료를 체크한 세트에는 세 값 모두 필요합니다.
- 하지 않은 세트는 완료를 체크하지 않습니다. 완료된 세트가 하나도 없으면 저장하지 않습니다.
- 보조운동/자유운동은 운동명 수정, 종목 추가·삭제, 세트 추가·삭제가 가능합니다. RIR로 기록하며 RPE만 기억한다면 `RIR ≈ 10 − RPE`로 환산합니다.
- 입력 중인 세션은 IndexedDB에 임시 저장됩니다. **나중에 계속 → 이어서 기록** 또는 재실행 후 이어서 기록할 수 있습니다.
- 완료 버튼을 누르고 **저장 후 재조회 검증 완료**를 확인해야 완료 기록입니다. 임시 저장만으로 사이클이 바뀌지 않습니다.

## 4. 3대운동 규칙

상세 기준은 앱 **프로그램** 메뉴에서 항상 확인할 수 있습니다. 모든 규칙은 `progression.js`의 rule version 1로 고정합니다.

| 구분 | 기본 규칙 |
|---|---|
| 중량 단위 | 20kg 바벨, 양쪽 합계 5kg. 일반 중량은 가까운 5kg으로 반올림. 웜업·Primer·백오프는 내림. 최소 20kg |
| 척도형 | 웜업 3세트 → Primer 85% × 1 → 척도 약 80%, 5–8회, 기준 6회, RIR 1 → 백오프 1세트 |
| Primer | RPE 7 이하. 85%라도 RPE 7을 넘을 것 같으면 감량/생략. 이후 3–5분 휴식 |
| 척도 증량 | 현재 척도중량 이상, 완료·기술 충족·8회 이상·RIR 1 이상이면 다음 척도 +5kg. 그 외 유지 |
| e1RM | 실제 5–8회, RIR 0–2, 완료·기술 충족일 때만 `중량 × (1 + (반복 + RIR)/30)` |
| PR 예약 | 6–8회, RIR 1–2, e1RM ≥ `(실제 1RM+5)×1.025`를 해당 리프트 척도형에서 연속 2회 충족 |
| PR일 | 척도 대신 현재 1RM +5kg 1회 시도. 기술 성공 여부 사용자가 판정 |
| PR 성공 | 실제 1RM 갱신, 해당 리프트 척도·근비대 누적 증량 0, PR 예약 해제. 다음 PR 자동 연속 예약 없음 |
| PR 실패 | 첫 실패는 같은 중량 재도전. 두 번 연속 실패는 예약 해제하고 다시 척도 평가 |
| PR 보류 | 실패로 세지 않고 예약 유지. 새 세션에서 척도 세트로 전환 가능 |
| 근비대 스쿼트/벤치 | 기준 약 70%. Set 1: 6–8회/RIR 2, Set 2: 같은 중량 8–10회/RIR 2, Set 3: −5kg 10–12회/RIR 3 |
| 근비대 데드 | Set 1/2: 6–8회/RIR 3, Set 3: −5kg 6–8회/RIR 3 |
| 근비대 증량 | 3세트 모두 현재 추천중량 이상·상한 반복 이상·목표 RIR 이상·완료·기술 충족이면 다음 +5kg. 단순 미달은 유지 |
| 백오프 | 스쿼트/벤치 70% 8–12회/RIR 2. 데드 65% 6–8회/RIR 3 |

e1RM은 추정값입니다. **실제 1RM은 PR 성공 또는 수동 변경으로만 바뀝니다.** RIR 보정 Epley, PR의 2.5% 여유·2회 확인, 두 번 실패 회귀는 이 앱의 보수적인 설계 선택으로, 검증된 개인별 성공 예측 공식이 아닙니다. Primer의 급성 효과도 보장하지 않습니다. 근비대 80%·근력 20%는 목적의 우선순위이며 세트 수를 정확히 80:20으로 나눈다는 뜻은 아닙니다.

참고 연구:

- [Robinson et al., 2024: 실패 근접도와 근비대·근력 메타회귀](https://pubmed.ncbi.nlm.nih.gov/38970765/)
- [Grgic et al., 2022: 실패·비실패 훈련 메타분석](https://pubmed.ncbi.nlm.nih.gov/33497853/)
- [Garbisu-Hualde et al., 2021: 고강도 사전 자극 체계적 문헌고찰](https://pmc.ncbi.nlm.nih.gov/articles/PMC8120977/)

연구는 실패 훈련의 필요성 및 피로와 수행 향상의 균형에 관한 방향을 참고한 것입니다. 앱 전체 처방이 연구에서 직접 검증되었다는 의미가 아닙니다.

## 5. 캘린더, 수정·삭제, 수동 1RM

날짜를 누르고 운동 기록을 선택하면 컨디션, 선택부위, 당시 1RM, 추천·실제 세트, e1RM, PR, 메모를 볼 수 있습니다. 같은 날짜에 여러 세션을 저장할 수 있습니다.

저장 직전에 원본 checksum을 다시 확인하며, 수정·삭제 전에는 전체 원본 snapshot을 저장하고, 변경 이벤트와 snapshot을 같은 transaction에서 처리한 뒤 baseline부터 전체 재생합니다. 당시 추천값·당시 1RM은 역사적 사실로 보존합니다. 수정으로 후속 PR 자격이 사라지면 기록에는 불일치를 표시하고 현재 1RM 갱신에는 반영하지 않습니다.

**진행 순서는 완료 순번 `seq`입니다.** 캘린더 날짜 수정은 표시 날짜만 변경합니다. 날짜순으로 운동 순서를 재배열하지 않습니다. PR 평가와 근비대 증량은 재생 시점의 현재 기준으로 판정합니다.

수동 1RM 변경은 데이터 메뉴에서 5kg 단위로 입력합니다. `manual_1rm_adjustment` 이벤트로 남고 해당 리프트의 진행 기준·PR 예약을 재설정합니다. 수동 이벤트를 취소하려면 전체 기록에서 해당 이벤트를 삭제합니다.

## 6. JSON 백업 및 복구

**내보내기:** 데이터 → JSON 백업 내보내기 → 다운로드 폴더 확인. 이름에 날짜와 시각 식별값이 들어갑니다. 주기적으로, 특히 앱 업데이트·기기 변경 전에 백업하세요. 개인 기록 JSON을 공개 GitHub 저장소에 올리지 마세요.

백업에는 앱·schema 버전, 내보내기 시각, baseline/사용자 설정, 운동·수동 이벤트, PR 이력, checksum이 포함됩니다. PR 이력은 편의상 함께 내보내며 복구 시 최종 근거는 baseline+events입니다. 미완료 임시 입력과 과거 snapshot 전체는 일반 백업에 포함하지 않습니다.

**불러오기:** 데이터 → 백업 불러오기 → JSON 선택 → 이벤트 수·운동 수·1RM 미리보기 확인 → 교체 확인. 병합이 아니라 **전체 교체**입니다. 현재 원본을 snapshot으로 보존하고 JSON 검증 후 사용자 확인을 받아 transaction으로 교체·재조회합니다. 확인창이 열린 동안 다른 탭에서 원본이 바뀌면 교체를 거부합니다. 잘못된 JSON, checksum, 지원하지 않는 schema는 거부합니다. JSON을 손으로 수정하면 checksum 때문에 거부됩니다.

브라우저는 다운로드 요청 이후 사용자가 파일을 취소/삭제했는지 앱에 보장해주지 않습니다. 진단의 내보내기 시각은 다운로드 요청 시각입니다.

## 7. Recovery Mode

DB open/read, 현재 원본 checksum/schema, 저장 후 검증에 문제가 있으면 일반 저장을 중단합니다. 기존 사용 흔적·snapshot·DB witness가 있는데 원본이 비어 있어도 복구 모드입니다. 자동 빈 초기화·DB 삭제 기능은 없습니다.

1. **사이트 데이터 삭제/초기화를 하지 마세요.**
2. 가능하면 **손상 포함 원본 내보내기**로 보존합니다. 이 원시 파일은 진단용이며 일반 JSON 가져오기에 바로 넣는 형식은 아닙니다.
3. **JSON 백업**, **긴급 미러**, **안전 snapshot** 중 검증되는 원본을 미리보기 후 선택합니다.
4. DB 연결 자체가 실패한 경우 다른 앱 탭을 닫고 재시도해야 합니다. 연결할 수 없는 DB를 앱이 강제로 덮어쓰지 않습니다.
5. 해결되지 않으면 진단 화면과 오류를 캡처해 문의하세요.

모든 브라우저 저장소와 사용 흔적이 동시에 지워지면 첫 실행과 구별할 수 없습니다. 따라서 첫 화면에서도 자동 저장하지 않고 사용자가 새 시작 또는 백업 가져오기를 명시적으로 선택합니다.

## 8. 앱 업데이트

1. 먼저 JSON 백업을 내보내고 실제 파일을 확인합니다.
2. 새 앱 파일을 **같은 저장소·같은 HTTPS origin**에 업로드합니다. DB 이름은 바꾸지 마세요.
3. `APP_VERSION`, `DATA_SCHEMA_VERSION`, `CACHE_VERSION`은 각각 별개입니다. 코드 변경만으로 schema를 올리지 않습니다.
4. 앱 파일이 변경되면 `service-worker.js`와 `progression.js`의 CACHE_VERSION을 함께 변경합니다. 예: 현재 `app-shell-2` → 다음 `app-shell-3`. APP_VERSION도 적절히 올립니다.
5. 앱이 새 worker를 감지하면 **새 버전이 있습니다 → 업데이트**를 표시합니다. 운동을 완료하고 다른 탭을 닫은 뒤 누르세요.
6. 다시 열어 진단 화면의 이벤트 수와 최근 날짜를 확인합니다.

서비스워커는 UI 파일만 캐시하며 DB API를 사용하지 않습니다. 자동 skipWaiting/clients.claim을 사용하지 않습니다. 사용자 업데이트 클릭 시에만 대기 worker를 활성화합니다.

요청의 network-first HTML은 권장 사항이었으나, 본 구현은 **승인 전 구버전 HTML/JS의 혼합을 줄이기 위해 동일 버전 app shell cache-first**를 선택했습니다. 캐시가 없으면 network, 오프라인 탐색에는 cached index.html을 사용합니다. worker 설치가 모든 shell 파일을 성공적으로 가져온 뒤 완료됩니다. GitHub 업로드는 파일별 수동 교체를 길게 나누지 말고 한 커밋으로 묶는 것이 좋습니다.

**Migration:** 이번이 첫 공개 schema v1입니다. v1은 무손실 검증·복사를 지원합니다. 없는 v0 형식을 추측하거나 향후 v2를 자동 변환하지 않고 거부합니다. 향후 schema 변경 시 `schema.js`에 명시적인 변환기를 추가하고, 원본 snapshot을 먼저 저장한 뒤 검증→transaction 적용해야 합니다. 지금 지원하지 않는 버전의 자동 변환은 없습니다.

## 9. 데이터 진단

App/schema/cache/실행 worker 버전, DB 연결, 이벤트 개수, 6사이클·자유운동 횟수, 최근 운동일, revision, 마지막 저장 검증, 영구 저장, 사용량/quota, 긴급 미러, 마지막 JSON 내보내기 요청을 표시합니다.

저장소별 역할:

- IndexedDB `ledger`: checksum이 포함된 baseline+event log 전체 원본.
- `snapshots`: 변경 전 전체 원본. 자동 삭제하지 않으며 장기적으로 공간을 사용합니다. 공간 부족으로 transaction이 실패하면 원본을 유지하고 오류를 표시합니다.
- `drafts`: 미완료 세션. 현재 progression의 근거가 아닙니다.
- `meta`: 저장 witness 및 내보내기 시각.
- localStorage: 사용 흔적과 긴급 mirror. primary DB가 아닙니다. 용량 제한으로 mirror 저장이 실패하면 경고하며, 이미 검증된 IndexedDB 저장은 유지합니다.

다중 탭은 revision 비교로 오래된 화면의 덮어쓰기를 거부합니다. 충돌 시 새로고침 안내가 나타납니다. 브라우저별·기기별 자동 동기화는 지원하지 않습니다. 다른 GitHub Pages 프로젝트도 같은 사용자 도메인을 공유하므로 기존 앱이 같은 origin의 저장소 전체를 지우는 코드를 실행하면 영향을 받을 수 있습니다. 별도 DB 이름만으로 같은 origin의 다른 코드에 대한 격리는 보장되지 않습니다.

## 10. 파일 구조 및 개발자 테스트

- `app.js` / `styles.css` / `index.html`: 화면·입력

- `db.js`: 저장·checksum·snapshot·import/export·복구
- `crypto-utils.js`: Web Crypto 우선 사용, UUID 및 SHA-256 호환 처리
- `service-worker.js`: app shell만 관리

- `tests/core.test.mjs`: Node 내장 테스트 38개
- `tests/browser.html`, `tests/browser.mjs`: 별도 QA DB를 사용하는 실제 브라우저 저장·복구 테스트 20개와 모바일 폭 확인 화면
- `TEST_REPORT.md`: 검증 결과와 미검증 항목

Node.js 22 이상에서 이 폴더를 열고 `npm test` 또는 `node --test tests/core.test.mjs`로 재실행할 수 있습니다. 외부 npm 의존성은 없습니다. Node 테스트는 로직과 서비스워커 모의 환경 검증을 포함합니다. 배포 주소 뒤에 `/tests/browser.html`을 붙이면 별도 테스트용 DB에서 브라우저 통합 테스트를 실행할 수 있습니다. 테스트 후 작은 QA DB가 남지만 실사용 DB를 수정하거나 삭제하지 않습니다. 어느 테스트도 Android 실기기 검증을 대체하지 않습니다.
## v1.1.0 변경 사항

- 웜업 1·2·3은 RIR을 비워도 완료 저장할 수 있습니다. 중량·반복수는 필요하며 본세트와 보조운동 RIR 조건은 유지됩니다.

- 종목명으로 부위를 추정하며 보조·자유운동에서 부위를 직접 수정할 수 있습니다. 미분류 종목을 알려주며, 미완료·0회 세트와 웜업·준비 세트는 부위별 본세트 집계에서 제외합니다. 자유운동에서 선택한 부위는 수행 세트가 있을 때 빈도에만 포함됩니다. 복합종목 부위별 집계는 합산하면 중복될 수 있습니다.
- 기록 수정·삭제·백업 복원 시 리포트가 재계산됩니다. 원본 snapshot과 JSON 백업에도 포함됩니다. 데이터베이스 이름·버전·사이트 주소는 그대로 유지됩니다.
- 전달은 앱 내 자동 표시 및 사용자가 누르는 공유/텍스트 다운로드 방식입니다. 별도 문자·이메일·ChatGPT 자동 전송이나 백그라운드 푸시는 없습니다.
- 업데이트: 앱의 새 버전 안내에서 업데이트를 누릅니다. 진행 중인 운동을 먼저 저장하고 다른 앱 탭을 닫아주세요. 앱이나 사이트 데이터를 지우지 않습니다.


## v1.2.0 — 직전 수행 기록

새 세션은 1RM 기반 중량·반복 추천 대신 같은 종목/데이의 직전 세트 실적을 표시합니다. 날짜순(같은 날짜는 저장 순서)으로 조회하며 과거 기록 수정 시 미래 기록을 제외합니다. 오늘 입력은 빈칸으로 시작합니다. 보조운동은 ‘검색 / 새 종목’에서 기존 이름을 선택하거나 새 이름으로 추가합니다. 운동 저장 후 검색 목록에 남으며 JSON 백업에도 포함됩니다. 띄어쓰기/영문 대소문자는 동일하게 처리하고 서로 다른 이름은 자동 병합하지 않습니다.

새 기록은 ruleVersion 2를 사용하며 자동 증량/PR 예약을 적용하지 않습니다. 기존 ruleVersion 1 기록과 백업은 보존됩니다. DB 이름 및 버전을 변경하지 않습니다. 1RM 수동 관리와 12회 리포트는 유지합니다.

검증: Node 테스트 9개 통과, 기존 백업 검증 및 직전 기록 조회 확인. 실제 Android 화면/오프라인 동작은 이 환경에서 검증하지 못했습니다.

## v1.3.0 — 종목 관리와 저장 용량 관리
